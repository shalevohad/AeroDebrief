## Problem Statement

**Before:** When opening a recording file, the amplitude graph showed synthetic test frequencies (251-260 MHz) instead of the actual frequencies from the recording. Users saw "Unknown frequency" warnings and couldn't interact with their real data.

**Root Cause:** `UnifiedGraphViewModel` was initialized with `AmplitudeSeriesProvider()` (parameterless constructor), which operates in "synthetic data mode" for testing.

### 4. Connected Real Data on File Load
**File:** `src/AeroDebrief.UI/Controls/UnifiedPlayerControl.xaml.cs`

```csharp
private void OnFileLoaded(string filePath)
{
    // Get recording data sources
    var packetSource = ViewModel.SessionManager.PacketSource;
    
    // Create audio engine for amplitude extraction
    var audioEngine = new Core.Audio.AudioProcessingEngine();
    
    // Create provider with real data pipeline
    var amplitudeProvider = new Services.Graphs.AmplitudeSeriesProvider(
        packetSource, 
        audioEngine);
    
    // Connect to ViewModel
    ViewModel.GraphViewModel.SetDataSource(amplitudeProvider);
    
    _logger.Info("? GraphViewModel connected to real recording data!");
}
```

**Impact:** Graph now loads actual recording frequencies instead of test data.

## Technical Notes

### Why Two-Step Initialization?

1. **Immediate UI:** App starts with synthetic provider ? UI loads instantly
2. **Real data on demand:** File opens ? Switch to real provider ? Real data loads

This avoids:
- Slow app startup waiting for file
- Null reference exceptions before file load
- Complex conditional logic throughout ViewModel

### AudioProcessingEngine Creation

We create a new `AudioProcessingEngine` instance for amplitude extraction. This is lightweight and only used for decoding audio packets to extract amplitude envelopes.

### Memory Efficiency

The `FilePacketSource` is **memory-mapped**, so it doesn't load the entire recording into RAM. Only the tiles needed for the current viewport are loaded, making this efficient even for large recordings.
